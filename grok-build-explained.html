0這是什麼

Grok Build（CLI 名為 grok，建置產物名為 xai-grok-pager）是 xAI 開發的 終端機 AI 編碼代理人。它以全螢幕 TUI 的形式執行，能理解你的 codebase、編輯檔案、執行 shell 指令、 搜尋網頁、管理長時間任務——可以互動式使用、headless（供 scripting/CI）執行、 或透過 Agent Client Protocol（ACP）嵌入編輯器。

它的定位與 Claude Code、OpenAI Codex CLI、opencode 屬同一類產品——事實上原始碼中還內建了 codex 與 opencode 兩套工具的 port（見 第 9 章）。這份 repo 是從 xAI 內部 monorepo 定期同步出來的 公開鏡像，以 Apache-2.0 授權，目的是原始碼透明化與本地建置。

💡 為什麼用 Rust + 全螢幕 TUI？
AI coding agent 要長時間駐留、頻繁串流大量 token、同時管理子進程與檔案系統——這對延遲與記憶體穩定性 很敏感。Rust 提供無 GC 停頓的可預測效能與強型別安全（整個 codebase 幾乎禁 unsafe）。全螢幕 TUI（相對於逐行印出的 CLI）則讓 scrollback、即時串流、modal、滑鼠互動、圖片內嵌成為可能——本質上是把「終端機」當成一個 GUI framebuffer 在經營。

💡 為什麼 crate 切這麼細（84 個）？
三個動機：(1) 建置平行化——像 xai-grok-shell-base、-session-support 純粹是從巨大的 shell crate 拆出來 以獨立平行編譯、避免每次改 shell 就全部重編。(2) 依賴反轉——xai-grok-auth、xai-grok-config-types、 xai-tool-types 這類「型別/trait seam」讓上下層不必互相直接依賴。(3) 版本隔離——xai-grok-mcp 專門 隔離需要 reqwest 0.13 的 rmcp，xai-mixpanel 取代 mixpanel-rs 以免拉進 reqwest 0.11，避免同一二進位裡塞多份 HTTP stack。

crates/ 三個子群的判準

  • crates/codegen/（62 個）— 應用主體。命名慣例 xai-grok-*（產品專屬）與 xai-*（可重用基礎工具，如 xai-ratatui-*、ptyctl）。
  • crates/common/（11 個）— 供應商中立的共用抽象，可被 grok 以外的 xAI 產品重用；特別是「xAI Computer Hub」工具協定與 Tool trait（禁 unsafe、避免 I/O）。
  • crates/build/（1 個）— 建置期工具：xai-proto-build，protobuf 編譯（透過 DotSlash 解析 bin/protoc）。

判準大致是：會不會被非 grok 的產品重用（→ common）、是不是只在 build 時跑（→ build）、其餘皆歸 codegen。

4建置流程

建置需要三樣東西協同：pinned Rust toolchain、DotSlash（hermetic 工具下載器）、protoc（protobuf 編譯器）。 下圖是從零到跑起 TUI 的管線。

rustup DotSlash cargo 讀 rust- 解析 bin/protoc 讀 Cargo.toml toolchain.toml （hermetic 下載 + Cargo.lock │ protobuf 29.3） │ ▼ │ ▼ 安裝 Rust 1.92 ──────────┴──────► xai-proto-build ──► 各 crate 編譯 ──► xai-grok-pager + rustfmt/clippy （protoc 供 proto codegen） （62+ crates） （官方安裝時改名 grok）

需求

  • Rust — rustup 依 rust-toolchain.toml 自動安裝 1.92.0。
  • DotSlash — hermetic 工具管理器，讓 bin/ 下的工具（尤其 bin/protoc）能下載並執行。cargo install dotslash。
  • protoc — proto codegen 透過 DotSlash 解析 bin/protoc（protobuf 29.3），或退回 PATH / $PROTOC。
  • 支援的建置主機：macOS 與 Linux；Windows 為 best-effort（未從此 tree 測試）。

cargo run   -p xai-grok-pager-bin            # 建置並啟動 TUI
cargo build -p xai-grok-pager-bin --release  # release 二進位：target/release/xai-grok-pager
cargo check -p xai-grok-pager-bin            # 快速驗證（不產生二進位）

# 開發時務必指定單一 crate（full-workspace build 很慢）

🔒 建置硬化（security）
.cargo/config.toml 對 Linux musl 目標套用 Full RELRO + non-executable stack （-Wl,-z,relro,-z,now,-z,noexecstack），防 GOT 覆寫、lazy binding 利用、stack shellcode。 發行 profile release-dist 使用 thin LTO + codegen-units=1；預設 --release 為了本地開發速度不啟用這些。

Build profile 對照

Profile用途特徵

⛓️ panic = "abort" 的連鎖影響
出貨的 CLI（dev/release/release-dist）都用 panic = "abort"——panic 直接終止進程，不做 unwind。這帶來更小的二進位與 更快的執行，但也讓 std::panic::catch_unwind 形同無效。後果之一：渲染「不受信任的模型生成 Mermaid」時無法用 catch_unwind 在進程內攔截 panic，於是被迫改成子進程 re-exec + SIGKILL 隔離的設計（詳見 第 11 章）。 這是一個「底層 build 決策向上決定了架構」的典型例子。

關鍵設計：整個 runtime 採 actor 模型。ChatStateActor（對話狀態）與 SessionActor（每個 session 的 turn 引擎）各自擁有一個 tokio task，透過 channel 溝通，熱路徑上沒有鎖。

💡 actor 模型如何避免鎖？
傳統做法是把共享狀態包在 Arc<Mutex<State>>，每個要讀寫的 task 先搶鎖——高併發下容易競爭、死鎖、或在串流熱路徑上卡頓。 actor 模型反過來：狀態只被單一 task 擁有，其他人不直接碰狀態，而是把「命令」（如 push_assistant_response） 透過 mpsc channel 送給那個 task，需要回覆時附一個 oneshot sender。於是所有變更天然序列化、無鎖、可單元測試。 Grok Build 有兩個這樣的 actor（chat state、session），彼此也只透過 handle + channel 溝通。

7進入點與模式分派

二進位的進入點是 fn main()（同步，非 #[tokio::main]），位於 crates/codegen/xai-grok-pager-bin/src/main.rs（約 3,077 行）。

這個 crate 是組合根（composition root）——之所以獨立存在，是為了同時 link xai-grok-pager 與可選的 xai-grok-pager-minimal 渲染模式（避免 cargo cycle）， 並在啟動時安裝 IoC hooks（jemalloc allocator 統計、heap-profile hooks）。#[global_allocator]（jemalloc）、 rustls、混淆相依都住在這裡，讓 xai-grok-pager lib 本體保持乾淨。

啟動序列

  1. Pre-runtime IoC install：xai_grok_pager_minimal::install()、jemalloc hooks、maybe_run_render_subprocess()（Mermaid worker 短路）、raise_fd_limit()、validate_requirements()、Sentry、crash-handler。
  2. 手動建構 tokio runtime：new_multi_thread().enable_all()，再 run_and_shutdown(rt, async_main(), grace=2s)——用 block_on + shutdown_timeout 讓卡住的 blocking task 無法拖住結束。
  3. async_main()：安裝 rustls provider → PagerArgs::parse_and_apply_cwd()（clap Parser）→ 依 flag 設環境變數、解析並套用 sandbox profile。
  4. 模式分派（見下）。

  None if 有 --single/--prompt-json/--prompt-file
       => xai_grok_pager::headless::run_single_turn(...)   // 一次性 headless
  None  => xai_grok_pager::app::run(args, ...)             // 互動式 TUI
}

run_agent_command() 再依 AgentCmd（Stdio / Headless / Serve / Leader）分派，並透過 resolve_use_leader(...) 決定是否進入 leader 模式。

Turn cycle 逐步（對應圖 B 的 ①–⑦）

核心迴圈在 session/acp_session_impl/turn.rs 的 process_conversation_turn（約 line 1693，內含 loop {…}）。每一圈：

  1. drain 待處理的 interjections / skill reminders / monitor events；注入首回合 memory + MCP reminder。
  2. check_auto_compact_needed()——若超過 threshold（預設 85%）先 run_compact_only()。
  3. 組出 effective_tools（若需要 JSON schema 但 backend 無法原生約束，會合成一個 StructuredOutput 工具；backend search 開啟時移除 web_search）。
  4. chat_state_handle.build_request()——向 ChatStateActor 要一份 ConversationRequest，蓋上 x-grok-* headers（session/turn/agent/deployment id）。
  5. run_turn_via_sampler(request)——auth refresh + config push，然後 sampler_handle.submit_and_collect()。串流 chunk 即時以 ACP AgentMessageChunk 送出。可能回傳控制流變體 CompactAndResubmit / RefreshAuthAndResubmit（continue 迴圈）。
  6. 記錄 token usage，把回應項目推回 chat state。
  7. 取出 tool_calls：
    • 空 → turn-end 路徑：跑 TodoGate（若還有未完成 todo，注入 <system-reminder> nudge 並續跑，上限 max_fires_per_prompt）、最終 interjection drain、驗證 structured output → 回傳 TurnOutcome::Completed。
    • 有 → dispatch 工具（見下），檢查 max_turns，再迴圈（工具結果已在 chat state，下一次 build_request 會帶上）。

值得一提的工程細節

  • Auth retry schedule：硬編 1s/2s/4s 指數退避（有測試釘住），註解記載這是為了避開曾造成「11.6 天 sleep」的 from_millis(1000) 陷阱；每次成功回應就重置（一個長 turn 可能跨越多次每小時 token 輪替）。
  • Compaction 兩段預燒（two-pass prefire）：在低於 threshold 約 10% 時就背景跑 pass-1 摘要，pass-2 命中時很便宜；fingerprint_prefix 守護 cache 在編輯/rewind 後的有效性。Grok Build 用 full-replace 風格（整個 session 摘要替換）。
  • Subagents：由 task 工具觸發，spawn 一個隱藏的子 SessionActor（SessionThread），共享父的 hunk tracker、FS、terminal、MCP pool；深度上限為 1（子代理不能再生子代理）。spec 由 xai-grok-subagent-resolution 以「override > role > persona > parent」優先序解析。
  • Interjection：xai-interjection-core 提供 mid-turn 插話緩衝，drain 時每則包成一個獨立的合成 user message，不合併。

核心 trait：Tool

定義於 crates/common/xai-tool-runtime/src/tool.rs：

pub trait Tool: Send + Sync {
    type Args:   for<'de> Deserialize<'de> + JsonSchema + Send + 'static;
    type Output: Serialize + ToolOutput + Send + 'static;
    fn id(&self) -> ToolId;
    fn description(&self, ctx: &ListToolsContext) -> ToolDescription;
    fn capabilities(&self) -> ToolCapabilities { ... }
    fn should_list(&self, ctx: &ListToolsContext) -> bool { true }
    fn execute(&self, ctx, args) -> impl Future<Output = ToolStream<Self::Output>>;
    fn run(&self, ctx, args)     -> impl Future<Output = Result<Self::Output, ToolError>>;
}
  • Schema：由關聯型別 Args 宣告（須實作 serde::Deserialize + schemars::JsonSchema），JSON Schema 透過 description() 回傳的 ToolDescription.arguments_schema 暴露給模型 API。
  • 回傳：ToolStream<Output>，不變式為 [Progress(_)*, Terminal(Result)]——任意多個 progress，結尾恰一個 terminal。
  • 型別抹除：Tool 因有關聯型別而非 object-safe，靠 blanket impl<T: Tool> ToolDyn for T 產生 object-safe 的 ToolDyn（ArcTool = Arc<dyn ToolDyn>）。
  • 路由：ToolDispatch::call(tool_id, args, ctx)。
  • 依賴注入：xai-grok-tools 內的工具從 Resources（TypeId-keyed 異質容器）讀取 Terminal/Cwd/FileSystem/Params<T>/State<T> 等，而非透過函式參數。

💡 為什麼要 ToolDyn 這層抹除？
Tool trait 有關聯型別（Args/Output），所以不是 object-safe，無法放進 Vec<Box<dyn Tool>>。 靠一個 blanket impl<T: Tool> ToolDyn for T 產生 object-safe 的 ToolDyn（其 execute 收發 serde_json::Value）， 就能把所有異質工具統一存進 registry、以 ArcTool = Arc<dyn ToolDyn> 動態 dispatch，同時保留具體工具端的強型別。

10Workspace 與 VCS 抽象

xai-grok-workspace 是宿主端核心庫：FS、VCS、權限、tool config、session 生命週期、hub server。所有工具的檔案讀寫都經過它。

workspace 是「agent 的手」實際碰到真實世界的地方。它的關鍵設計是把所有檔案存取抽象成一個 trait， 於是同一套工具程式碼可以無差別地跑在本機、ACP 編輯器託管、或遠端 proxied 的檔案系統上。

檔案系統：一個 trait、多個後端

核心 trait 是 AsyncFileSystem（src/file_system/fs.rs）：root()、read_file、write_file、delete_file。

為何不統一用一套 git 函式庫？因為 git2（libgit2 綁定）擅長讀出結構化資料，而某些寫入操作用 git CLI 更穩、更貼近使用者預期； worktree 與快速 index 讀取則 gix（純 Rust）最快。於是三者各司其職：

Action → dispatch（純同步、sans-IO、回傳 Vec<Effect>）→ effects（spawn async task）→ TaskResult → 再 dispatch。 事件迴圈（app/event_loop.rs 的 run()）是單一 biased 的 tokio::select!，只做 IO 管線。dispatch 刻意保持無 IO、可單元測試。

Grok 不用 ratatui 內建的 Terminal::draw，而是自訂 draw_frame，把每一幀包在「同步更新」區塊裡，並精算游標指令與差異：

BeginSynchronizedUpdate（DEC 2026，告訴終端「先別畫，我一次給」） │ ▼ autoresize → get_frame → 執行 render 閉包（填 buffer + 收集 LinkSpan） │ ▼ set_frame_links → flush_with_links（diff_large：只重寫變動的 cell） │ ▼ CursorState::action() 去重： ├─ 這幀無變化且游標同位 ─► 送 0 bytes（保留游標閃爍） ├─ cell 變了 ─► MoveTo └─ 顯示切換 ─► Show / Hide │ ▼ PostFlush escapes（如 Kitty 圖片資料） │ ▼ EndSynchronizedUpdate → flush 到專屬 writer thread（經 mpsc，不卡 tokio）

關鍵渲染工程

  • 繞過 ratatui 的 Terminal::draw：因為它每 frame 都無條件送 Show+MoveTo，會重置游標閃爍計時器（30fps 下游標看起來變實心）。自訂 draw_frame 用 CursorState::action() 去重，idle frame 送出零 bytes（保留閃爍）。
  • Synchronized output（DEC 2026）：每 frame 包在 BeginSynchronizedUpdate/End 內，tmux/zellij 下不閃爍/撕裂。
  • 非同步 writer thread：frame bytes 經 mpsc 送到專屬寫入執行緒，PTY 反壓只卡那條執行緒、不卡 tokio 迴圈。
  • diff_large：修掉 ratatui 上游把 cell index 轉 u16 導致 >65,535 cells 時 UI 擠到角落的 bug（420×160 = 67,200 cells）。
  • 虛擬化 scrollback：以累計 virtual_y 高度做 O(1) 增量捲動；可重用 scratch buffer。
  • 串流/checkpoint markdown：凍結已定案前綴、只重繪尾端，把 naive O(N²) 串流重繪降到約 O(N)；開放的 code fence 用 resumable syntect 增量高亮。
🛡️ Mermaid 的 out-of-process 渲染
完整 PNG 由 pager re-exec 自己成 xai-grok-pager __mermaid-render 子進程 惰性、跨進程渲染， 從不 inline 畫——而是開系統圖片檢視器。原因：出貨 CLI 以 panic = "abort" 建置，使得 crate 內的 catch_unwind 形同無效；不受信任的模型生成 Mermaid 可能 abort 整個 pager。子進程 panic/timeout/非零退出會被 run_with_timeout（真 SIGKILL 收 process group）隔離並退回 code block。inline 顯示的則是自製的 Unicode box-drawing 文字藝術。

Inline 圖片

透過 Kitty graphics protocol（Ghostty/WezTerm/Warp 亦支援）；iTerm2 對映為 None（缺 placement-id/z-index/source-crop 基元，無法讓圖片隨文字格捲動）。

14ACP 編輯器嵌入

ACP（Agent Client Protocol）是一套標準協定，讓任何編輯器都能把 Grok 當成「AI 後端」來驅動，而不必為 Grok 寫專屬整合。 這也是 Zed、Neovim、Emacs 能共用同一個 agent 的原因。

Grok 以 ACP agent 的身分嵌入編輯器。xai-acp-lib 建於外部 agent-client-protocol crate 之上，提供型別化的 message/channel/gateway 層。協定是 JSON-RPC over stdio。

💡 為什麼是 JSON-RPC over stdio？
stdio（標準輸入/輸出）是最通用、最無依賴的進程間通訊方式——任何語言、任何平台都能 spawn 一個子進程並讀寫它的 stdin/stdout，不需要 socket 權限、port 協商或網路堆疊。JSON-RPC 則是輕量、人可讀、有明確 request/response/notification 語意的協定。 兩者相加，讓「編輯器 spawn grok agent stdio 就能對話」變得極其簡單。normalize_json_line 還特別繞過 Foundation/Xcode 把 / escape 成 \/ 的相容性問題。

🔐 requirements 層為何要 Ed25519 簽章 + fail-closed？
requirements.toml 承載企業政策（例如「禁止 always-approve 模式」）。若它只是普通檔案，使用者可自行竄改繞過。因此它靜態簽章， Grok 啟動時驗簽；驗證失敗可設定成 fail-closed（直接拒絕啟動），確保政策無法被本機使用者掏空。這是 B2B 部署的信任根基。

16Sandbox 沙箱

沙箱的目的：限制 agent（尤其它跑的 shell 指令）能碰的檔案與網路，把「模型犯錯或被惡意 prompt 誘導」的損害範圍框起來。 預設關閉，但對不信任的任務強烈建議開啟。

xai-grok-sandbox 在進程啟動時套用 OS 層沙箱，基於 nono crate（包裝 Linux Landlock 與 macOS Seatbelt）。子進程網路以 seccomp 阻擋（Linux）。

┌─ Landlock（kernel LSM） 路徑讀寫白名單 │ │ 但 Landlock 沒有「deny 特定路徑」原語 │ ▼ ├─ bubblewrap (bwrap) re-exec 補 deny： │ --ro-bind（寫拒絕）· bind-over chmod-000（讀拒絕）· devbox 的 /data │ └─ seccomp 阻擋子進程網路（restrict_network 時）

  • 啟用：--sandbox <profile>、GROK_SANDBOX、[sandbox] profile。自訂 profile 於 ~/.grok/sandbox.toml（extends/read_only/read_write/deny）。
  • Linux deny//data：Landlock 無 deny-path 基元，故以 bubblewrap（bwrap）re-exec 強制（--ro-bind 寫拒絕、bind-over chmod-000 讀拒絕）。
  • 專案設定只能新增 profile、不能重定義全域 profile（防惡意 workspace 掏空企業 profile）。事件記於 ~/.grok/sandbox-events.jsonl。
🛡️ 為什麼「專案只能加、不能改」？
沙箱設定可放在專案的 .grok/sandbox.toml。但如果專案能重定義全域 profile，一個惡意 repo 只要附上一份把 strict 改成「全開」的設定，就能在你 clone 它、跑 agent 的瞬間掏空你的企業沙箱政策。因此專案層只能新增自訂 profile， 不能覆蓋全域既有 profile——這是對「不受信任的 workspace」的縱深防禦。
