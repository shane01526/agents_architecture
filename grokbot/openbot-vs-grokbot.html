同一個詞、兩件事:兩套「一群 Bot 幫你工作」的系統

CopilotKit 的 OpenBot 與 Grok Bot 0.18 表面上像到不可思議 —— 都把 agent 叫「Bot」、都給每個 Bot 一台自己的電腦、都在意稽核與 human-in-the-loop。但只要往下挖一層就會發現:「多 Bot」在兩邊根本是兩件事,而且它們各自補上了對方最大的缺口。這一頁做逐維度對照,並在最後給一份實際的組合建議。

一句話定位

◉OpenBotCopilotKit · MIT · alpha

自架的多人 Web 平台。Docker Compose 起全部元件、資料在你自己的 PostgreSQL、模型你自己給。三個範例同事是設定而非程式碼(agents.yaml)。

核心賣點是一句話:「Every action decided before it happens and recorded after.」—— 一切經過一個 gateway 決策並留下紀錄。

  • 形態:Web App + 多服務容器
  • 使用者:多人,SSO / SAML / OIDC / RBAC
  • Bot = Postgres 一列,或任何 AG-UI 端點
  • 框架:中立(LangGraph / Mastra / CrewAI / Pydantic AI / ADK / 手寫)
◆Grok Bot 0.18閉源產品 · 非官方重建

單人桌面 App。Electron(macOS/arm64),側邊欄養很多個 Bot,每個有自己的 persona、記憶、排程,而且彼此會互相傳訊息、可以拉群聊。

核心賣點是「一群會協作的 AI 同事住在你的桌面上」,工作跑在一個叫 box 的遠端/本機容器裡。

  • 形態:桌面 App + 遠端沙箱
  • 使用者:單人(使用者是唯一 principal)
  • Bot = ~/.grokbot/agents/<id>/ 一個資料夾 + 一顆 SQLite
  • 框架:綁自家 runtime(重建版加了四後端改道)

先給你三句話

① 「多 Bot」在兩邊是兩件事
Grok Bot = 多 Bot 協作。Bot 之間真的會互相講話:1:1 私訊會喚醒對方一個隱藏 turn、群聊有 round-robin 編排器(3 輪 / 10 則 / @mention / (pass))。
OpenBot = 多 Bot 分工 + 路由。一個 channel 一開就被 pin 到一個 coworker,所謂多 agent 是一個 LLM intent router 在挑「這題該找哪個專才」。Bot 之間目前不能互相講話 —— 這在原始碼裡是明文的「later」。→ 四條證據
② 治理 vs 協作,各強一邊,而且剛好互補
OpenBot 補上了 Grok Bot 最大的缺口:治理是機制而非 prompt —— 單一 gateway 咽喉點、CEL policy、fail-closed、先寫審計列才動作、per-Bot 授權矩陣。
Grok Bot 補上了 OpenBot 最大的缺口:多 Bot 協作的完整實作、本機 markdown 記憶、8 種事件觸發的自主性、六種中斷續跑路徑。
→ OpenBot 的治理 · → Grok Bot 的協作
③ chief / member:兩邊 runtime 都沒有階層,但缺席的位置不同
Grok Bot:Bot 彼此是對等 teammate,沒有任何 Bot 能命令或刪除另一個。它有一個叫「Chief of Staff」的 persona 模板,但那只是一段文字,拿到的工具跟其他 Bot 一模一樣。
OpenBot:連 persona 模板都沒有。它的階層長在人那一側 —— admin / member 的 RBAC、/admin/people 升降權、revoked_access。
換句話說:Grok Bot 把治理成本放在「維持透明度」,OpenBot 放在「設計權限系統」。

★ 核心差異

★ 「多 Bot」的兩種意思:協作 vs 路由

這是整頁最重要的一章。兩套系統都讓你養一群 Bot,但那群 Bot 之間發生了什麼事,完全不同。Grok Bot 的 Bot 會互相講話;OpenBot 的 Bot 各自待在自己的頻道裡,由一個路由器決定該找誰。這個差異決定了後面所有事情:要不要輪數上限、要不要防扇出、要不要跳數上限。

並排看一次:同一句話進到兩套系統會發生什麼

情境:使用者說「幫我查一下這家供應商的風險,順便跟研究那邊確認最新財報」。

◆Grok Bot:Bot 會去找 Bot多 Bot 協作
使用者 ──▶ 風險 Bot(lane: user) │ │ system prompt 裡有「同事名錄」(≤40 位) │ 模型決定呼叫 SendToAgent(研究Bot, "…") │ ├─ 風險 Bot 的 transcript ← assistant(toAgent) ├─ pendingAgentInbound[研究Bot].push(msg) ├─ 工具回傳「已送出,別等」 ← 拿不到回覆 └─ 風險 Bot 繼續自己的事 / 結束這一輪 │ ▼ 研究 Bot 的 transcript ← user(fromAgent) 排入研究 Bot 的佇列(lane: agent) 隱藏 turn:「[agent] …from 風險Bot」 ├─ 研究 Bot 有完整工具箱,真的去查 ├─ 選項一:SendToAgent 回去 ──┐ └─ 選項二:什麼都不做(允許沉默)│ ▼ 風險 Bot 又被喚醒(另一個獨立 turn) └─ SendMessage 告訴使用者結果

兩個 Bot 永遠不可能在同一輪裡來回對話 —— 因為每個 Bot 是一條獨佔佇列,同輪等待必然死鎖。所以 fire-and-forget 是唯一解,不是效能選擇。

◉OpenBot:路由器去找 Bot多 Bot 分工
使用者 ──▶ server │ │ 這是新 channel 嗎? │ ├─ 是,且使用者沒有 @ 指名 │ └─▶ intent router(一次模型呼叫) │ 讀每個 coworker 的 roleDescription │ + reaches[](它實際握有哪些連接器) │ → 挑一個 → 寫 channel.routed 審計列 │ → 失敗/沒把握 → 落到 default coworker │ ├─ 使用者有 @ 指名 → 不需要決定 │ └──▶ channel 被 PIN 到那一個 coworker 「for the life of its thread」 │ ▼ 該 coworker 全程負責這個 thread ├─ 它自己去查(browser / shell / MCP) ├─ 每個工具呼叫都回 server gateway 過閘 └─ 答案回到同一個 channel ✗ 它無法把工作轉給別的 coworker ✗ 它無法喚醒別的 coworker ✗ 沒有多 Bot 同場對話的編排器

要換人只能由人操作:開一個新 channel、或在訊息裡 @ 指名另一個 coworker。

1「OpenBot 的 Bot 不能互相講話」—— 四條證據

證據一:channel 一開就被 pin 到一個 coworker
server/src/routing/classify.ts
檔頭註解
classify.ts — Choosing which coworker an untagged message is for A channel is pinned to one coworker for the life of its thread, and the pin is set before the first turn runs, so this decision happens at channel creation, not during a run. When the person named a coworker with @, there is nothing to decide and this is never called.
關鍵在 "not during a run":路由是一次性的、發生在對話開始之前。一旦 pin 定了,那個 thread 就是那一個 coworker 的,沒有中途換手的路徑。
證據二:work queue 明文寫出「今天有什麼、以後才有什麼」
server/src/db/schema/work.ts:37
workItems.kind 的註解
work.ts — /** What kind of work. */ computer.suspend today; routines and bot-to-bot hops later.
同一個檔案的檔頭也說得很清楚:"ONE MECHANISM, THREE FEATURES. Suspending idle computers needs it, scheduled routines need it, and a hop from one Bot to another needs it. Written once with all three in view rather than three times slightly differently…"

所以這不是遺漏,是刻意先把地基蓋好。這張表已經把難的部分做完了:誰擁有一個 item、擁有者死掉怎麼辦、復原會不會跑兩次(lease / attempts / finishedAt 保留而非刪除 / key 帶「due 的那一分鐘」當幂等鍵)。→ 這正是移植藍圖的立足點
已驗證:只有一個 kind
server/src/work/ 只有兩個檔案(culler.ts / queue.ts),而 culler.ts 定義的 CULL_KIND = "computer.suspend" 是整個 repo 唯一被使用的 work kind。沒有任何 bot.hop / routine.* 之類的 kind 存在。
證據三:檔頭標題寫了 handoff,但表還沒建
server/src/db/schema/coworker.ts:2
檔頭寫著:"Coworker tables: bots, skills, routines, bot-to-bot handoff."

已規劃未實作 —— 標題是這個檔案將來要放什麼的宣告,不是現況清單。這是本頁最容易誤讀的一處:只看標題會得出完全相反的結論。
證據四:資料模型支援多 Bot,但沒有編排器去用它
server/src/db/schema/core.ts
channel_agents
它確實是多對多:primaryKey({columns:[channelId, agentId]})。而且 channels.lastMessageAgentId 的註解明說:"Which agent spoke, so a channel with several can show the right one."

也就是說:「一個 channel 掛多個 Bot」在資料層是可以表達的,UI 也預期得到。但 沒有任何程式碼會在一個 turn 裡輪流叫這些 Bot 發言 —— 沒有 round-robin、沒有輪數上限、沒有「誰該回話」的解析、沒有 (pass) 之類的略過協定。能表達 ≠ 有行為。

◆ Grok Bot 這邊的最大缺口上表最後三列是關鍵:1:1 私訊完全沒有機制層的節制。一個沒對齊或被 prompt injection 影響的 Bot,可以在單一 turn 內連發多則 SendToAgent,每則喚醒一個新 turn,而被喚醒的 Bot 又能再寄 —— 系統層沒有任何東西阻止指數擴散。

它的替代防線是「使用者全程看得見」(每一跳雙邊 transcript 都留痕)+「三車道永遠讓人優先」。在單人桌面 App 情境下說得過去,移到多人環境就失效,因為透明度不再等於可控。
◉ OpenBot 這邊的相對優勢(同一個問題)因為 Bot 之間還不能互相講話,這個攻擊面現在不存在。更重要的是:當它將來實作 bot-to-bot hops 時,那些 hop 會走 work_items(有 lease、有 attempts 計數、有幂等 key)並且每個工具呼叫仍然要過 gateway —— 也就是說,它的協作層一出生就會落在治理層之內,而不是像 Grok Bot 那樣長在治理層旁邊。這是架構順序帶來的差異,不是誰比較用心。

3chief / member:兩邊都沒有,但缺席的位置不同

◆Grok Bot:Bot 對等,人是唯一 principal
  • 沒有任何 Bot 能刪除或封存另一個 Bot(連自己都不行)。prompt 原文:"You have no tool to delete or archive an agent … never destroy one (yourself included)." 只有使用者能從側邊欄右鍵刪除。
  • UpdateAgent 可改別人的名字/描述,但是 merge-only:只改你傳的欄位,設計上無法清空或破壞對方 profile。
  • profile.json 只有 {name, description, title, avatarShape, avatarColor} —— 沒有 parentId / ownerAgentId / managerId。
  • 工具集由能力可用性決定(有沒有 box、有沒有連 MCP),不依 Bot 身分。
  • UI 那張叫 org-chart(組織圖)的畫面,實作上只有 membership(房間→成員)與 message(無向)兩種邊,而且用力導向布局而非樹狀。
  • 「Chief of Staff」是 onboarding 模板陣列裡的一個 persona(描述 "Manages your other Bots and pulls you in for decisions"),與 Night Shift、QA Engineer 結構完全相同。
◉OpenBot:階層長在人那一側
  • Bot 之間沒有階層,也沒有通道 —— 連 persona 模板層級的「主管 Bot」都沒有。
  • 真正的階層是人的 RBAC:user_roles 表、INITIAL_ADMIN_EMAILS(唯一能產生 admin 的來源,每次登入重讀)、/admin/people 升降權與移除、revoked_access 表(結束當前 session 並阻擋下次登入)。每次變更都上審計。
  • Bot 的「歸屬」是對人而非對 Bot:agent_profiles.ownerUserId + visibility: public|private。私有 Bot 只有作者看得到。
  • 能力歸屬也是對 Bot 而非 Bot 之間:plugin_grants (kind, ref, agentId) —— 誰能呼叫什麼工具是一張明確的表,由 admin 授予。→ Grok Bot 沒有這張表
  • skills 的設計特別能說明它的權限哲學:任何登入者都能寫 skill,因為 "a skill adds no capability";而加 MCP server 是 admin 的決定。「指令」與「能力」被刻意分開。
結論
兩套系統的 Bot 之間都沒有 chief / member。差別在於那個空缺被什麼補上:
Grok Bot 用「透明度 + 人是唯一 principal」補;OpenBot 用「人的 RBAC + per-Bot 授權矩陣」補。
前者在單人桌面上更便宜也更有效(你自己就是那個 chief,不需要在 Bot 之間再造一層官僚);後者在多人/多租戶環境是唯一可行的答案(透明度無法擴展到你看不到的人身上)。如果你要做的是企業內部的 AI 同事平台,後者是必須的,前者是不夠的。
一個容易混淆的分層「Bot 之間沒有階層」不等於「整個系統沒有階層」。兩邊都有另一個軸上的真階層:
◆ Grok Bot — Task 派出的 subagent(父可 CheckSubagent 讀狀態、MessageSubagent 強行插指令、StopSubagent 直接拆掉)與 CloudAgent(破壞性動作需 confirm:true)。
◉ OpenBot — 平台層沒有 subagent 概念;但掛在 channel 上的那個 Bot 內部可以是任意複雜的 agent 圖(LangGraph 等),那是 Bot 自己的事,OpenBot 不介入也不治理其內部結構(只治理它打出來的每一個工具呼叫)。

1單一咽喉點:沒有不留紀錄就動作的路徑

server/src/computer/gateway.ts — 檔頭 The only way an action reaches a Bot's computer.

Reading a page is one thing; clicking a button on an external website is another, and the difference is the whole product. The record is not a report written alongside the work, it is the thing the action goes through, so it cannot be missing: an action that was not recorded did not happen, because there is no path that acts without writing the row first.

2最關鍵的一步:不信任模型送來的標籤

server/src/computer/gateway.ts — 檔頭(接續) Step 1 is the one that is easy to skip and fatal to skip. A gateway that decides on a label supplied by the model is theatre: "never click Submit" is evaded by sending {ref: "e13", name: "Continue"}. The refs are opaque to the caller precisely so that the server holds the mapping.
為什麼這一段值得單獨背下來市面上大多數「agent 動作審核」的實作,審的是模型自己描述的那個動作。這在對抗性條件下等於沒審 —— 模型(或影響模型的注入內容)可以把「按下送出」描述成「按下繼續」。

OpenBot 的做法是:ref 對呼叫方是不透明的,對應關係只有 server 有,而且是從 server 自己抓的 snapshot(computer_snapshot 表 / snapshot-store.ts)解出來的。所以 policy 看到的 element.name 是真實 DOM 的,不是模型聲稱的。

3CEL policy:表達力、優先序、失敗方向

server/src/computer/policy.ts — 檔頭 CEL instead of a rule table. The boundary a company wants is a sentence: "never click anything that says Submit on a page outside our own domain". A table of columns can express the shapes we thought of; an expression language can express the one they thought of. This is also the language the enterprise gateway already speaks, so a rule written here means the same thing there.

Precedence: deny beats allow. A rule that removes permission must never be defeated by a broader rule that grants it, or a company cannot reason about what it has forbidden.

deny 先於 allow

deny 任一條為真就拒絕,不管 allow 說什麼。理由寫得很清楚:否則「公司無法推理自己禁了什麼」。

缺 policy = 全禁

allow: [] 代表什麼都不許。空 policy 不是「沒設定所以放行」。

壞規則 = 拒絕

壞掉的 deny 規則 拒絕;壞掉的 allow 規則 不放行。"Submit order" 這種字串本身是合法 CEL(能 parse、求值成一個字串)—— 這類「合法但不是布林」的情況也被處理。

dry-run vs enforce

dry-run 照樣決定與記錄,但全部放行。理由:"A governance feature nobody dares switch on is not a governance feature." 讓 operator 先對真實流量寫規則、讀審計,再開啟。

malformed 就不啟動

AGENT_COMPUTER_POLICY 的 JSON 壞掉,server 直接拒絕啟動,而不是靜默退回預設。

字串輔助函式

cel-js 0.8.2 沒實作任何字串方法,所以自己註冊了大小寫不敏感的 contains() / matches() 當 CEL global —— 否則 element.name.contains("Submit") 這種最常見的規則根本寫不出來。

isDisplayed(已在畫面顯示過 ⇒ 重送時不重複顯示)+ isRedriven(已重送過 ⇒ 只重送一次)。「至少一次投遞」與「畫面冪等」用兩個 bool 就解決了。

房間 turn 每一步都比對 currentTurnEpoch(session) === epoch。使用者又送了新訊息 ⇒ 舊那場沒必要跑完。

成員失敗 = pass

群聊成員 turn 拋錯就吞掉當作 pass。註解:"A failed member turn is a pass, not a room-wide failure." 一個 Bot 壞掉不該讓整場對話崩掉。

跨通道狀態洩漏的顯式處理

成員在群聊 turn 中被私訊搶佔 → 重送時附 buildGroupRedriveNote(),用自然語言告訴它:「你上次這個 turn 被一則直接訊息打斷,房間還沒看到你的任何回覆,你在處理那則私訊時說的話留在那個私聊裡。已經做完事的話,現在用 SendMessage 送進房間。」

最細膩的一段設計上面最後一格值得展開。它承認了一件多數系統會忽略的事:兩條通道會互相干擾,而干擾之後 agent 的世界觀是錯的(它以為自己已經回覆過了,其實那些話留在別的聊天室)。

處理方式不是靜默丟棄、也不是硬性回滾,而是用自然語言把干擾後的正確行為講清楚。這是「prompt 作為狀態修復機制」的一個罕見且恰當的用法 —— 因為要修的正是模型的認知狀態,而那本來就只能用語言修。

使用者的請求在隊首等待 … ├─ 等超過 watchdogMs │ └─▶ stage:"trip" → interruptWedgedRun(agentId),標記 phase="interrupted" ├─ 再等 watchdogGraceMs 還沒結束 │ └─▶ stage:"escape" → 直接 resolve 掉它、丟進 zombies 集合、 │ queue.active = null、立刻 pump 下一個 │ (zombie 之後真的結束時只上報 stage:"late_settle") ▼ 使用者的請求開始執行
「逃生」而不是「殺死」escape 階段並沒有真的殺掉那個 Promise —— 在 JS 裡做不到。它做的是放棄等待、把它移出 active 位置、承認它可能還在背景跑(所以叫 zombie,並持續追蹤到它自己結束)。這是對「活性優先於整潔」的務實取捨,而且每一次發生都被遙測記下來(含 waitingUserAgeMs,所以「使用者被卡了多久」是可量化的)。
◉ OpenBot 的對應物:設計方向一樣好,覆蓋面還小work_items 這張表的品質很高,註解甚至把三個易錯點列出來:"who owns an item, what happens when the owner dies, and whether a recovery can run something twice." 具體做法:
• lease(claimedBy + leaseUntil)—— 過期即自由,"it needs no process to notice a death, only the next claim to look at the clock"
• attempts 計數而非狀態 —— "A RECLAIMED ITEM IS NOT A FRESH ONE":第一次派出的 item 確定沒跑過,第二次的可能已經花過錢了,接手的人必須能區分
• finishedAt 保留而非刪除 —— 曾經因為完成後刪列,導致 07:00 的 routine 被晚醒的副本重新提供而跑第二次;"A finished row is the collision."
• Postgres 而非 queue —— for update skip locked,無 coordinator、無 leader election、加副本加吞吐量

結論:OpenBot 的地基比 Grok Bot 更適合多副本(Grok Bot 本質單副本),但目前只承載一個 work kind。

5subagent:另一軸上的真階層

工具能做什麼語意重點
Task把一塊自成一體的工作交給 subagent,一律背景跑,派出後父 Bot 立刻拿回控制權類型固定清單(generalPurpose / explore / shell / computerUse / browserUse / debug / cursorGuide / videoReview / watchVideo / custom);模型只能從允許清單選,不在清單就明確告知使用者、不准自行替換
CheckSubagent唯讀查狀態:跑多久、最近工具呼叫、一條可直接 Read 的即時 transcript 路徑描述明說「不是為了輪詢完成 —— 完成時你會自動被復活」,而是為了發現卡住或繞圈
MessageSubagent強行把指令插進正在跑的 subagent,它中斷當前步驟、讀你的話、帶著原有 context 繼續不重來。典型用途:computerUse subagent 卡在某元件、告知「使用者剛登入了」、或要它收尾回報
StopSubagent直接拆掉,釋放它的桌面視窗,不再回報與 Message 的分工寫得很清楚:改方向用 Message,消失用 Stop
一個有趣的能力界線父 Bot 看不了影片。system prompt 明文要求:遇到影片就派 watchVideo subagent 去看,並且不准用 Shell 讀影片位元組、不准聲稱自己看過。

這是「用階層補足能力缺口」的具體案例 —— subagent 不只是為了平行化,也是為了掛載不同模態的模型。◉ OpenBot 平台層沒有這個概念:它把「Bot 內部怎麼組織」完全交給 AG-UI 端點自己(可以是任意複雜的 LangGraph 圖),只治理它打出來的每一個工具呼叫。這是兩種都合理的分工哲學。
🎯 Convergent design

🎯 兩個團隊獨立收斂到同一結論的 8 件事

這一章可能比任何單邊的分析都有用。兩套沒有任何關係的系統(一個是 xAI/Anysphere 的商業產品、一個是 CopilotKit 的開源專案)在這 8 個問題上做出了幾乎一樣的選擇。當兩個獨立團隊在同一個問題上收斂,那個選擇大概就是對的 —— 而如果你要自己做一套,這 8 條就是最不該重新發明的部分。

這章怎麼推的 / 什麼算「收斂」
判準
只收「兩邊都有具體實作、而且解法的形狀相同」的項目。單純「兩邊都有稽核功能」不算(那是必然);「兩邊都刻意把拒絕與允許分成不同事件類型」才算。
排除
排除了兩邊做法差很多的項目(例如記憶、治理),那些在各自的強項章節。也排除了純粹因為技術棧相同而一致的東西(都用 TypeScript、都用 SQL)。
限制
「獨立收斂」是推論而非事實 —— 兩個團隊都可能讀過同一批公開討論、或看過對方的產品。這裡主張的是結論一致,不是主張彼此不知情。
1都把 agent 對使用者叫「Bot」,對程式碼叫 agent
◉ OpenBot
產品名就是 OpenBot;README 通篇 "a Bot"、"per-Bot"、"which Bots may use them"。但資料表叫 agents / agent_profiles,路由叫 /agents,環境變數叫 AGENT_TOOL_TOKEN。
◆ Grok Bot
產品名 Grok Bot;onboarding 模板描述寫 "Manages your other Bots"。但目錄叫 agents/,常數叫 SAND_SEND_TO_AGENT_TOOL_NAME,型別叫 SandAgentProfile。
為什麼會收斂
「agent」對一般使用者太抽象也太學術;「Bot」有現成的心智模型(它會幫我做事、它不是人)。而工程上「agent」是既有的技術詞彙,換掉會讓程式碼與整個生態脫節。兩邊都選了「產品用一套詞、程式碼用另一套」而不是強求統一。
2一個 Bot 一台自己的電腦(而不是共用一個沙箱)
◉ OpenBot
supervisor 為每個 Bot 建一個 container:自己的 Chromium profile、自己的 /workspace volume。README:"the supervisor gives each Bot its own container, its own /workspace volume and its own browser profile."
◆ Grok Bot
「box」:遠端沙箱容器,或(重建版)本機 Docker 容器。每個 Bot 的工作在自己的 box,有 forever-box 與交接機制。
為什麼會收斂
因為 Bot 要持有真實登入狀態。一旦 Bot 需要「以我的身分登入 Salesforce 並保持登入」,共用瀏覽器就等於共用身分,而「A Bot 用了 B Bot 的 session」在畫面上與日誌上都看不出來。OpenBot 把這件事講得最清楚,而且做了一個很漂亮的處理 —— 見下面第 4 條的 isolation_loaded。
3都把「動作碰的是哪台機器」做進邊界,而不是做成一個參數
◆ Grok Bot:用命名
Shell / Read / AwaitShell(box 內)vs ExternalShell / ExternalRead / ExternalAwaitShell(使用者主機)。兩組平行的工具名,而不是同一個工具加 {target: "host"|"box"} 參數。
◉ OpenBot:用架構
computer 只在 container 裡,而且它本身不做 policy 決策;要碰使用者本機服務需要 AGENT_COMPUTER_ALLOW_PRIVATE_HOSTS,而該旗標在 NODE_ENV=production 下設了就拒絕啟動。
為什麼會收斂
因為「這個動作有沒有碰到我的真實機器」是稽核上最重要的一個二元問題,而它不該藏在參數裡。用不同工具名的好處:模型每次選工具都得明確決定、稽核日誌上一眼看得出來。用架構隔離的好處更徹底:根本沒有那條路徑。兩者都拒絕了「一個工具加一個 target 參數」這個看似最簡潔的做法。
4都堅持記錄「拒絕」與「失敗」,而不只記「允許」
◉ OpenBot
三態:action_allowed / action_refused / action_failed。理由寫在原始碼裡:
• 兩者都記的原因 —— "a trail that records only what was permitted cannot answer whether the Bot tried."
• 失敗要獨立一類的原因 —— "'allowed' reads as 'happened', and a trail that cannot tell those apart misleads exactly when it matters most."
• 還有 bot.declined:模型在呼叫任何工具前就拒絕,gateway 看不到,所以另記一列。「什麼都沒發生」也是一個事實。
◆ Grok Bot
錯誤不吞:trays.pushError({agentId, title, detail}) 把「另一個 Bot 傳來的訊息處理失敗」「群聊失敗」「廣播失敗」推到使用者可見的托盤。搶佔留痕:reportTurnInterrupt({reason:"agent_steer", hadActiveRun, wasInFlight})。排程器記 trip/escape/late_settle 三個階段 —— 每一次「使用者被卡住」都可量化。
額外:OpenBot 的 isolation_loaded
這是本條最漂亮的延伸。沒有 supervisor 時全部 Bot 共用一個瀏覽器,而「畫面一樣、審計一樣、Bot 用了別的 Bot 的 session 看起來跟正常一模一樣」 —— 產品裡沒有任何東西能區分,所以就在開機時把「這個部署是哪一種」記在審計裡,寫在事後無法爭辯的地方。同樣思路的還有 policy_loaded(這次啟動實際生效的邊界)。

教訓:當兩種狀態的所有可觀測跡象都相同時,唯一的辦法是主動宣告。
5都不讓 secret 進 transcript
◉ OpenBot
README:"Secrets never enter the transcript: the trail records that a secret was requested and how long it was, not what it said." 憑證存 /admin/credentials,加密於靜態、API 永不回傳、從審計 payload 遮蔽。mcp_servers.credentialId 是指標而非副本(vault 擁有加密/輪替/撤銷,第二份 token 只是第二個要記得撤銷的東西)。
◆ Grok Bot
secrets bridge 在 Electron main(唯一不接受任意輸入的行程),coordinator 與 host 都不持有 keychain、要用時向 main 索取。sand-secret-request.ts 處理 Bot 索取機密的流程。遙測用 redacted-protos(型別層面就沒有敏感欄位)。
為什麼會收斂
因為 transcript 是會被送進模型、會被存很久、會被複製到別處(遙測、除錯、鏡像)的東西。一旦 secret 進去了就再也拿不出來。兩邊都選擇「記錄事件而不記錄內容」。
6都把 human-in-the-loop 當一級功能,不是事後補的確認框
◉ OpenBot:Take the wheel
Bot 撞到登入牆或 2FA 會主動求助;控制權在同一個面板交接,記三個事件(help_requested / control_taken / control_released),而且記成一段期間而非逐個按鍵。

最關鍵的細節:人在開車時,Bot 的動作是「拒絕」而不是「排隊」(HumanHasControlError)。排隊會讓 Bot 累積一批動作在人放手的瞬間全部湧出;拒絕迫使它重新評估當前狀態。
◆ Grok Bot:七個閘 + widget
auto-review 對七個高風險面各有模式(hostShell / boxShell / mcp / computer / automationWrite / cloudAgent / subagentLaunch);SendMessage 可帶 question widget 徵求同意(prompt 明確要求「扇出前先用一個 question widget 說明你要找誰、要問什麼」);CloudAgent 破壞性動作需 confirm:true;VNC 可直接接手 box 桌面。
為什麼會收斂
因為兩邊的 Bot 都會遇到它不該獨自完成的事(登入、付款、不可逆操作),而「放棄任務」與「硬幹下去」都是錯的答案。第三條路 —— 停下來、把方向盤交出去、記錄這件事發生過 —— 是唯一可行的。
7都把危險能力關在一組窄詞彙後面(而不是用網路或密碼當邊界)
◉ OpenBot:supervisor 四個動詞
supervisor/src/index.ts — 檔頭 Access to the Docker socket is root-equivalent on the host because a container can be started with the host filesystem bound into it. Putting that in the API server would mean every bug in a request handler, every injection through a Bot's own output and every dependency in a large tree sits one mistake away from owning the machine.

So the socket lives behind four verbs, expressed in Bots rather than in Docker: ensure a computer for this Bot, stop it, reset it, list them. There is no passthrough and no way to name a container directly … A compromised API server can ask for a Bot's computer to be restarted. It cannot ask for anything else, because nothing else is expressible.

The shared secret is not the boundary; the vocabulary is. … Neither is the network the boundary, but it is the layer in front of both.
◆ Grok Bot:preload 窄橋 + box connector
renderer 拿不到 Node 能力,只能透過 preload 曝露的五種 frame(lifecycle/request/cancel/reply/event)說話,而且方向被嚴格區分(client 送 server 方向的 frame = 協定違約,直接斷線)。機密只在 Electron main —— 唯一不渲染模型輸出、不執行模型指令、不連任意網址的行程。
為什麼會收斂
因為兩邊都有「模型輸出會流過的程式碼」與「擁有作業系統級權限的程式碼」,而這兩者必須分開。而且兩邊都認識到:token / 網路分段只是防止誤觸,真正的邊界是「能表達的動作集合」有多小。這是本頁最值得記住的一句設計原則。
8兩邊的註解都在寫「為什麼」,而且把踩過的坑寫進程式碼
◉ OpenBot:甚至引 issue 編號
• classify.ts 記下 #178:intent router 對已帶 /v1 的 OPENAI_BASE_URL 又接了一次 /v1,導致每個設了該變數的部署全部 404 —— 而且「未加標籤的訊息靜默停止被路由,而且沒有任何東西說明為什麼」。URL 修好了;讓它沒被注意到的那個盲點,就是 RoutingUndecided 這個具名欄位。
• core.ts 記下 #82:channels.allowedGroups 這一欄「Written by synchronizeTenantPackage and read by nothing」—— 一個名字承諾了、卻沒有任何東西維護的控制。它把這件事寫在欄位註解裡而不是留給下一個人踩。
• mcp_servers.credentialId 記下一次真實事故:這一欄曾是 text 對 uuid 主鍵、沒有外鍵,資料庫願意持有一個指向不存在憑證的指標,而它真的發生了 —— 測試刪掉了憑證,這一欄指向空氣,連接器報「還沒註冊 OAuth client」而該列看起來仍然設定好了。"Nothing caught it because nothing was checking."
◆ Grok Bot:把不變式與理由寫進常數旁
• 每個生成檔頂端帶 @evidence 與 region SHA-256,聲明是從哪一段逐位元組相同的區段還原的。
• group-chat-orchestrator.ts 的一句話註解把四個不變式講完(bounded / epoch-cancellable / round robin / one room turn)。
• 註解會說明失敗語意:"A failed member turn is a pass, not a room-wide failure."、"Streaming preview failures must not fail the member turn."、"Preview cleanup is defensive: failures never fail the member turn."
為什麼這件事值得列進來
因為在 agent 系統裡,大部分的 bug 不是「程式碼寫錯」而是「安全/正確性的假設沒被寫下來,下一個人把它拆了」。這兩份 repo 都選擇把假設、理由、以及踩過的坑放在最靠近程式碼的位置。

如果你要從兩者身上抄一件事而只能抄一件,抄這個習慣的價值可能高於抄任何一段實作。
這 8 條合起來說了什麼
當一個 AI agent 能持有真實登入、跑真實指令、影響真實系統時,兩個獨立團隊都收斂到同一組結論:給它自己的機器、把危險能力關在窄詞彙後面、記下它試過什麼(不只做成了什麼)、不讓機密進對話、遇到不該獨自做的事就把方向盤交出去、並且把你為什麼這樣做寫在程式碼旁邊。
這 8 條沒有一條跟「模型多聰明」有關。它們全部是關於邊界、記錄、與交接 —— 也就是說,agent 系統的難處不在 AI,在系統工程。

◉ OpenBot:server 決定這個 Bot 這一輪拿到哪些工具 → Bot 打回來的每個呼叫都要過 gateway → policy 與審計必然生效。Bot 可以是任何人寫的、跑在任何地方,治理不會漏 —— README 說得很準:"the governance rides the protocol rather than the framework."

◉ OpenBot 的 xuser 對應物是「SSE notify + 4 秒長輪詢兜底」的推拉混合(createNotifyDrainGate:notify 連著就不必頻繁輪詢,斷了就回退)。

缺口清單:要自己寫什麼

缺口為什麼必要OpenBot 已有的立足點難度
① bot-to-bot 訊息通道 協作的前提。沒有它,「多個 AI 同事」只是「多個各自獨立的助理」。 預留了 work_items 的 kind 就是為此設計的(註解明寫 "bot-to-bot hops later")。lease / attempts / finishedAt 保留 / 幂等 key 全部已經做好。 中。主要是定義訊息 payload 與投遞後的喚醒路徑,不必碰基礎設施。
② 每 Bot 訊息配額與速率限制 Grok Bot 完全沒有這個,全靠 prompt —— 這是它最大的缺口。一個被注入影響的 Bot 可以連發訊息、每則喚醒一個新 turn。 部分 plugin_grants 的 (kind, ref, agentId) 形狀可以承載「這個 Bot 每小時可寄幾則」,但額度計數本身要新表。 低。一張計數表 + gateway 上的檢查。
③ 跳數上限(hop limit) 防 A→B→C→… 指數擴散。兩邊都沒有(Grok Bot 的群聊有輪數上限,1:1 沒有;OpenBot 還沒有通道)。 全新 但可以搭在 ① 的 payload 上:每則訊息帶 hops,超過就拒絕並記審計。 低,只要在 ① 一開始就設計進去。事後補很痛,所以第一版就要有。
④ Bot→Bot 授權矩陣 現在兩邊都是(或將是)全連通圖。企業內「風險 Bot 可以問研究 Bot,但業務 Bot 不能問法務 Bot」是常見需求。 幾乎現成 plugin_grants (kind, ref, agentId) 直接加一種 kind(例如 kind="bot-message", ref=<目標 botId>)。連 admin 授予的 UI 都能複用。 低。這是本清單裡投資報酬率最高的一項。
⑤ 端到端 trace id 兩邊都缺。Grok Bot 有 turn trace(beginTurnTrace,帶 sand.is_group_member 等屬性)但不跨 SendToAgent 邊界傳遞。當一個動作經過「Slack 事件 → Bot A → Bot B → subagent → shell」五跳,沒有單一 id 能串起來 —— 合規追溯會卡在這裡。 部分 audit_events 已有結構化 payload,加一個 traceId + parentSpanId 欄位即可;channel.routed 這種決策列也已經在記「為什麼」。 中。技術不難,難在要在每一條路徑上都傳下去(這正是 Grok Bot 沒做到的原因)。
⑥ 群聊編排器 只有在你真的需要「多個 Bot 在同一場對話裡輪流發言」時才需要。如果只需要「A 私下問 B」,①④ 就夠了。 資料層現成 channel_agents 已是多對多;channels.lastMessageAgentId 的註解顯示 UI 已預期多發言者。 中。可直接照抄 Grok Bot 的 107 行編排器邏輯(見下方清單)。
⑦ 排程 routines 「AI 同事」若不能自己在早上準備摘要,價值少一半。OpenBot 尚未實作。 預留了 work_items 的 key 已經設計成帶「due 的那一分鐘」當幂等鍵 —— 註解明說這就是把「再觸發一次」變成「插入一個已存在的列」的關鍵。 低到中。地基已在,要寫的是 cron 解析與定義的 CRUD。

群組不能包群組。沒有子群組、沒有樹 —— 否則喚醒的扇出無法推理。

正確性模式

「本輪我沒話說」。判定要寬鬆(接受 pass/(pass)/(pass). 等變體,對模型格式不穩定容錯),但保留字不能被當普通訊息貼出去。加分:streaming 預覽也判斷「目前字元是否還可能變成 (pass)」,避免卡片閃現又被刪。

不要抄的

✗ 靠 prompt 做治理

Grok Bot 的「不要扇出、不要轉述抱怨、不要 ping-pong」全部只寫在 prompt。在單人桌面上勉強可行(使用者馬上看到訊息暴增並手動介入),在多人環境會失效,因為透明度不再等於可控。用 OpenBot 的方式:能用機制擋的就別交給 prompt。

✗ 把 Bot 間通訊放在同一行程

Grok Bot 的私訊是 in-process Map,所以低延遲、沒有網路失敗模式 —— 但無法跨裝置、無法跨副本。企業部署必然多副本。用 OpenBot 的 work_items(Postgres + for update skip locked)。

✗ 從 URL 匯入可執行的指令

Grok Bot 的 workflow 可從 URL 匯入,而 workflow body 是會被當指令執行的自然語言 + helper script,沒有簽章或審核的跡象。受管環境要嘛關掉、要嘛加白名單 + 審核流程。對照 OpenBot 的 MCP 目錄哲學:加一個 vendor 等於做一次 vendor 審查。

✗ 讓 Bot 自己建 Bot(在企業環境)

Grok Bot 的 CreateAgent 是 Bot 手上的工具。在單人情境是貼心功能;在企業情境是繞過 Bot 註冊審核的路徑(新 Bot 該有什麼授權?誰是它的 owner?)。OpenBot 目前只有人能建 Bot,這是對的預設。

⚠️ 兩邊都要注意的風險

風險細節怎麼處理
◉ OpenBot 是 alpha官方自述 "Expect rough edges and bugs, and expect things to move." worker/ 目前是 stub({status:"idle"});compose 定義了 SPIRE 三個服務但 start.sh 不啟動;routines 與 bot-to-bot 未實作。當設計參考 + 起點,不要當生產底座直接上線。先自己跑一遍、讀 CHANGELOG(112 KB,更新很快)、評估 fork 成本。
◉ 兩個危險的預設值出貨 policy 是 deny:[] / allow:["true"](全允許);.env.example 預設 OPENBOT_SINGLE_USER=true(所有請求當同一管理員)。部署第一件事就是寫 policy 並刪掉 single-user。它做對了一件事:刪了 single-user 卻沒設 identity provider 時,server 拒絕啟動而不是把所有人當管理員。
◉ 外部服務依賴CopilotKit Intelligence 承載 threads / memory / realtime gateway,server 沒有 INTELLIGENCE_API_KEY 與 COPILOTKIT_LICENSE_TOKEN 就拒絕啟動。先決定:自架 Intelligence、接受託管、或自己做一層。這是選型決策不是實作細節,而且會影響合規審查。
◆ Grok Bot 不是原廠碼非官方逆向重建。模組名稱與邊界可能與原廠不同;frontend/ 僅為部分重建。把它當設計案例庫而非可移植的程式碼。抄機制與常數,不要抄檔案結構。
◆ 授權與智財它重建的是閉源商業產品。從中學習設計是一回事,直接複製程式碼到商業專案是另一回事 —— 這需要法務判斷,不是技術判斷。OpenBot 是 MIT,這一點乾淨得多。
最後一段:兩者共同給的最重要一課把兩份 repo 讀完,最強烈的印象不是任何一項功能,而是它們都把「為什麼」寫在程式碼旁邊,而且把踩過的坑留在原地當警告(OpenBot 甚至引 issue 編號)。

在 agent 系統裡,大部分事故不是「程式碼寫錯」,而是「安全或正確性的假設沒被寫下來,下一個人把它拆了」 —— 那個「一個表單有三道門」的故事就是最好的例子:如果沒有人把它寫進 key 欄位的註解裡,下一個重構的人一定會再拆一次。

如果從這兩套系統只能抄一件事,抄這個習慣的價值可能高於抄任何一段實作。
