用三條思路理解 Grok Build

Grok Build(CLI 名 grok、建置產物 xai-grok-pager)是 xAI 官方的 終端機 CLI coding agent ── 全螢幕 TUI、能編修檔案、跑 shell、搜尋網頁、管理長任務,可互動、可 headless(CI/腳本)、可經 ACP 嵌入編輯器。本文件基於公開原始碼鏡像(xai-org/grok-build,對應 monorepo commit 2ec0f0c8)整理,聚焦它如何用 Rust 的 actor 模型 + 84 個 crate 把一條 agent loop 疊成生產級產品。

𝕏 定位一句話Grok Build 是「官方 CLI coding agent」,與 ✳ Claude Code 同類(寫程式、接編輯器),不同於 OpenClaw/Hermes 主打「住在訊息軟體裡的個人助理」。差別在:Grok Build 用 Rust 寫、runtime 是無鎖 actor 模型、整包是 84-crate Cargo workspace。
一句話心智模型:Grok Build = 一條 agent loop + 兩個 actor + 84-crate 分層 + OS 級隔離。核心迴圈就是 process_conversation_turn:build_request → 串流呼叫模型 → 有 tool_call? → 並行執行工具 → append 結果 → loop。真正讓它「能用在真實開發」的,是圍繞這條 loop 的無鎖 actor 狀態管理、prompt queue、compaction、leader/follower、sandbox、MCP/hooks/ACP 擴充 ── 分裝在 84 個各司其職的 crate 裡。

路徑一 · 動態視角

🚶 一次 turn 的生命週期

跟著一次使用者提問,走完 process_conversation_turn 的完整迴圈。每站附「深入 →」連到元件詳解。來源:crates/codegen/xai-grok-shell/src/session/acp_session_impl/turn.rs

入口先決定模式互動 TUI、headless(-p)、ACP(grok agent stdio)三種入口都通到同一套 runtime(xai-grok-shell)。差別只在前端與進入點;turn 迴圈完全共用。
1

prompt 入佇列 ── pending_inputs

使用者訊息成為 SessionCommand::Prompt,推入 SessionActor 的 pending_inputs: VecDeque<InputItem>。maybe_start_running_task 若無 running task 就取出隊首、spawn 一個 turn task。

深入 → Actor Runtime
2

drain interjection + reminder

迴圈開頭清空待處理的 mid-turn 插話(xai-interjection-core)、skill/monitor reminder,並注入首回合的 memory + MCP reminder。

深入 → Agent Loop
3

check_auto_compact ── 必要時先壓縮

若 token 使用超過門檻(預設 85%),先 run_compact_only() 用 full-replace 壓縮整段對話再繼續。context 估算走 bytes/4 粗估。

深入 → Compaction
4

build_request ── 向 ChatStateActor 要請求

組出 effective_tools(需要 JSON schema 但 backend 無法原生約束時,合成 StructuredOutput 工具),再 chat_state_handle.build_request() 拿一份 ConversationRequest,蓋上 x-grok-* headers。

深入 → ChatStateActor
5

run_turn_via_sampler ── 串流呼叫模型

auth refresh + config push,然後 sampler_handle.submit_and_collect()。SSE 串流的 chunk 即時以 ACP AgentMessageChunk 送給前端。可能回傳控制流變體 CompactAndResubmit / RefreshAuthAndResubmit(continue 迴圈)。

深入 → Sampler/模型
6

記錄 usage + 推回 chat state

record_token_usage;回應項目(assistant/tool_result)推回 ChatStateActor。取出 tool_calls 準備分流。

深入 → chat state
7

tool_call? → 並行 dispatch(+權限)

有 tool_call:每個先過 pre-flight(MCP 解析 → arg 解析 → PreToolUse hook → 權限)。核准的以 FuturesUnordered 並行執行,觸及同檔者共用 per-file mutex 序列化。結果依 index 折回 → append → loop 回第 4 站。

深入 → Tools  深入 → Workspace
8

無 tool_call ── TodoGate → 收尾

無 tool_call 時跑 TodoGate:若還有未完成 todo,注入 <system-reminder> nudge 並續跑(上限 max_fires_per_prompt);否則 finalize、驗證 structured output,回傳 TurnOutcome::Completed。

深入 → 收尾邏輯

L1 · Actor 狀態

為何需要這層:agent 會併發跑很多事(串流、工具、背景任務),共享可變狀態若用鎖容易競爭/死鎖。用 actor 讓狀態被單一 task 擁有、以 channel 溝通,熱路徑無鎖。

1為什麼存在

把一次提問變成「行動 + 回覆」並維持可串流、可中斷、可壓縮,需要一條權威迴圈。這條迴圈跑在 SessionActor 派出的 turn task 裡,且同時服務互動 TUI / headless / ACP 三種入口。

2核心概念

loop + tool_call 分流 + 串流核心是「build_request → 串流呼叫模型 → 若有 tool_call 就並行跑、append、再呼叫;否則過 TodoGate 收尾」。整段是 AsyncGenerator 式串流,chunk 即時送 ACP。session/acp_session_impl/turn.rs

3運作機制

  • 三入口共用:互動 TUI(xai-grok-pager)/ headless(run_single_turn)/ ACP(run_stdio_agent)都通到 xai-grok-shell 的 turn 迴圈。
  • 迴圈內順序:drain interjection → check_auto_compact → 組 effective_tools → build_request → run_turn_via_sampler → 記 usage → 取 tool_calls → 分流。
  • 控制流變體:sampler 可回 CompactAndResubmit(context 超長)/ RefreshAuthAndResubmit(401)→ continue 重跑。
  • 收尾:無 tool_call → TodoGate(未完成則注入 nudge reminder 續跑)→ finalize → TurnOutcome::Completed。

5範例 / 設定

// 最小迴圈(概念,對應 process_conversation_turn)
loop {
  if check_auto_compact_needed() { run_compact_only().await }
  let req = chat_state.build_request(effective_tools).await
  let res = run_turn_via_sampler(req).await   // 串流 + retry
  chat_state.record_assistant_response(res)
  let calls = res.tool_calls()
  if calls.is_empty() {
     if todo_gate.should_nudge() { continue }  // 未完成 → nudge
     return TurnOutcome::Completed
  }
  execute_tool_calls(calls).await             // 並行 + per-file mutex
}

1為什麼存在

工具是 agent 對外界產生作用的唯一手段。要讓大量工具行為一致(schema/權限/串流輸出),且能被 registry 統一動態 dispatch,需要一個強型別 trait + 型別抹除層。

2核心概念

Tool trait → ToolDyn → registryTool trait 有關聯型別 Args(須 Deserialize + JsonSchema)與 Output;因非 object-safe,靠 blanket impl<T: Tool> ToolDyn for T 抹除成 object-safe 的 ToolDyn,存進 registry 以 ArcTool dispatch。crates/common/xai-tool-runtime/src/tool.rs

3運作機制

  • Schema:由關聯型別 Args 自動導出 JSON Schema,經 description() 的 ToolDescription.arguments_schema 暴露給模型。
  • 回傳:ToolStream<Output>,不變式 [Progress*, Terminal] ── 任意多 progress 結尾恰一 terminal。
  • 依賴注入:工具從 Resources(TypeId-keyed 容器)取得 Terminal/Cwd/FileSystem/Params<T>/State<T>,而非函式參數。
  • 5 namespace:同工具的不同呈現與相容 port。

// Tool trait(概念,crates/common/xai-tool-runtime/src/tool.rs)
pub trait Tool: Send + Sync {
    type Args:   Deserialize + JsonSchema + Send + 'static;
    type Output: Serialize + ToolOutput + Send + 'static;
    fn id(&self) -> ToolId;
    fn description(&self, ctx) -> ToolDescription;  // 內含 JSON Schema

★ Actor Runtime 架構

Grok Build 最獨特的設計:整個 runtime 是無鎖 actor 模型。這一章拆解兩個 actor 的分工、單執行緒 LocalSet + !Send 的取捨、以及 leader/follower 的崩潰重連。來源:xai-grok-shell/src/session/、xai-chat-state

核心命題agent runtime 會併發跑很多事(串流、多工具、背景任務、子代理),共享可變狀態若用 Arc<Mutex> 容易競爭/死鎖、且在串流熱路徑上卡頓。Grok 的答案:狀態只被單一 task 擁有,其他人以 channel 送命令 ── 天然序列化、無鎖、可單元測試。

三個 actor 的分工

1

MvpAgent ── ACP 前門

實作 ACP Agent trait,持有 session map 與 subagent coordinator,把 ACP JSON-RPC(session/prompt 等)翻成 SessionCommand 送給對應 SessionActor。agent/mvp_agent/

2

SessionActor ── turn 引擎(!Send)

每個 session 一個。主迴圈 run_session() 是 biased 的 tokio::select!,監聽 completion(turn 完成)、cmd(SessionCommand)、chat-state 事件、內部 SessionEvent、memory 計時器。持有 pending_inputs 佇列與 running_task。session/acp_session.rs

3

ChatStateActor ── 對話狀態擁有者(Send)

在自己的 tokio task 上跑,獨佔對話 Vec<ConversationItem>、usage ledger、pruning。外界只能經 ChatStateHandle(fire-and-forget 變更 + oneshot 查詢)存取,SessionActor 從不持鎖跨對話。crates/codegen/xai-chat-state

為何單執行緒 LocalSet + !Send?

!Send 的取捨SessionActor 與 MvpAgent 是 !Send(不能跨執行緒搬),全部跑在一個 tokio::task::LocalSet 上,用 spawn_local。好處:單執行緒內狀態存取免同步、RefCell/Cell 安全可用;代價:需要 LocalRef<T>(!Send 原始指標包裝)把 'static &T 餵進 spawn_local 閉包,附文件化的安全不變式。而 ChatStateActor 刻意做成 Send、跑在獨立 task,把「需要跨執行緒的對話狀態」與「單執行緒的 session 邏輯」切開。

leader / follower 崩潰重連

🏛️ 一機一 leader一台機器只跑一個 leader 進程,持有真正的 MvpAgent;各 client(TUI、IDE、headless WebSocket)經 Unix-domain socket 以 ACP 連上,client 只是薄橋接。LeaderReconnector + StdioReplayState 提供崩潰重連 ── 重放快取的 initialize 與每個 session/load(replay_acp_state_after_reconnect),TUI 崩潰後 agent 仍在背景存活可無縫接回。
為何值得agent 一個 turn 可能跑數分鐘。把 agent 抽到常駐 leader,front-end 可拋棄 ── TUI 崩潰、重開、換 IDE client 都能重連回同一個仍在推進的 session,也讓 dashboard 統一管理成為可能。

★ 生產級工程亮點

一個成熟 CLI agent 的工程量,大半花在「邊緣情況」而非主功能。這一章收錄 Grok Build 幾個「底層決策向上決定架構」與「為真實故障而生」的設計。來源:原始碼註解與 crate 文件

核心觀察下面每一項都不是炫技,而是踩過坑或想清楚後的防禦性設計。它們共同解釋了「為何一個 coding agent 需要 84 個 crate」。
① panic = "abort" 的連鎖影響
決策
出貨 build(dev/release/release-dist)全用 panic = "abort" ── panic 直接終止進程、不 unwind。更小更快,但讓 catch_unwind 形同無效。
後果:Mermaid 子進程隔離
渲染「不受信任的模型生成 Mermaid」無法在進程內用 catch_unwind 攔 panic → 改成 pager re-exec 自己成 __mermaid-render 子進程惰性渲染,子進程 panic/timeout 被 run_with_timeout(SIGKILL 收 process group)隔離,退回 code block。xai-grok-mermaid
後果:gix 執行緒預算
panic=abort + 緊 RLIMIT_NPROC 下,gix status 的 spawn_scoped 若失敗會 abort 整個進程 → xai-gix-status 限制 produce worker 執行緒數(上限 8)。
② 工具並行 + 同檔序列化
機制
核准的 tool_call 以 FuturesUnordered 全並行送出,但觸及同一檔案的(lock_path_for_args 取 file_path/path/target_file)共用 per-file tokio::sync::Mutex。
為何
最大化 wall-clock 並行,同時保證同檔編輯依模型送出順序序列化、不互相踩踏;背景 drainer 依 index 把結果確定性折回。
③ Auth retry 排程(一個真實 bug 的教訓)
硬編 1s/2s/4s
401 重試用硬編指數退避,有測試釘住。註解記載這是為避開曾造成「11.6 天 sleep」的 from_millis(1000) 陷阱。每次成功回應就重置(一個長 turn 可能跨越多次每小時 token 輪替)。
④ 為真實故障而生的 crate
xai-sqlite-journal
NFS 上 WAL 的 mmap -shm 會 SIGBUS → 本地磁碟用 WAL、網路掛載改用 rollback journal。
xai-system-power
跨平台 sleep/wake 通知 → 避免在筆電睡眠前一刻啟動 OIDC token refresh(醒來已過期)。
xai-circuit-breaker
HTTP circuit breaker(滑動視窗 + 最小樣本)→ 後端連續失敗時快速失敗,不狂重試打爆對方。
xai-grok-secrets
出站資料 regex 清洗 → 防 API key/路徑/email 隨遙測外洩(遙測本身可 opt-out)。
⑤ TUI 渲染:idle frame 送 0 bytes
繞過 ratatui draw
ratatui 內建 Terminal::draw 每幀都送 Show+MoveTo,會重置游標閃爍計時器(30fps 下游標看起來變實心)。Grok fork 了 ratatui Terminal,自訂 draw_frame 用 CursorState::action() 去重 ── 無變化的幀送出 0 bytes,保留閃爍。
同步輸出 + writer thread
每幀包在 DEC 2026 synchronized output(不閃爍/撕裂);frame bytes 經 mpsc 送專屬 writer thread,PTY 反壓只卡那條執行緒不卡 tokio 迴圈。
⑥ 為何 84 個 crate?
建置平行化
xai-grok-shell-base、-session-support 純為從巨大 shell crate 拆出、獨立平行編譯,避免每次改 shell 全部重編。
依賴反轉
xai-grok-auth、xai-grok-config-types、xai-tool-types 這類型別/trait seam 讓上下層不必直接互相依賴。
版本隔離
xai-grok-mcp 隔離需 reqwest 0.13 的 rmcp;xai-mixpanel 取代 mixpanel-rs 以免拉進 reqwest 0.11 ── 避免同一二進位塞多份 HTTP stack。
收束這些「瑣碎」設計正是「能跑的 agent」與「能出貨的 agent」之間的距離。它們也呼應本頁主題:一個底層決策(panic=abort、NFS、筆電睡眠、Windows verbatim 路徑…)往往在整個 codebase 掀起連鎖的防禦性工程。

🔎 Audit & Telemetry

🔎 稽核:留什麼 log、遙測給誰

Grok Build 的稽核分兩面:給使用者的 session 持久化(resume/rewind),與給 xAI/企業的遙測(可 opt-out)。與 Claude Code「遙測無法關閉」不同,這是 Grok 在稽核哲學上的差異點。

兩面 audit給使用者查核的是 session 記錄(supports resume/rewind);遙測(xai-grok-telemetry:product events + Mixpanel + Sentry + OTLP)則可經設定 opt-out,且出站前經 xai-grok-secrets regex 清洗(防 key/路徑/email 外洩)。

審查資料存哪

類別存放給誰查
Session~/.grok/sessions/<cwd>/<id>/(summary/updates/chat_history/plan/rewind_points…)使用者:resume/continue/fork、rewind、崩潰復原
遙測product events + Mixpanel + Sentry + OpenTelemetry(OTLP)xAI/企業:可 opt-out([features] telemetry=false / GROK_TELEMETRY_ENABLED=0);外部 OTEL 需雙重 opt-in
secrets 清洗出站前 regex 掃描防 API key/user 路徑/email 外洩
